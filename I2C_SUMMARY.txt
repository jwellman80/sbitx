================================================================================
                    I2C BUS CONTENTION - INVESTIGATION SUMMARY
================================================================================

CRITICAL BUG FOUND: "double!" warnings indicate race condition causing
I2C bus data corruption from concurrent thread access.

================================================================================
KEY FINDINGS
================================================================================

1. BROKEN SYNCHRONIZATION (i2cbb.c:196-199)
   - "Mutex" is just a static int counter, NOT a real pthread_mutex
   - No atomic operations
   - Allows reentrancy: just prints "double!" and continues
   - FAILS to prevent concurrent I2C access

2. MULTIPLE THREADS ACCESS I2C BUS
   - GTK UI Thread (1ms timeout callback)
   - Sound/DSP Thread (SCHED_FIFO real-time priority)
   - Calibration Thread (power band calibration)
   - Hamlib Network Thread (remote control)
   - WebServer/Telnet Threads (network control)

3. MOST CRITICAL: Si5351 CLOCK GENERATOR
   - Accessed from 5+ threads
   - Frequency changes happen at GPIO-level in i2cbb.c
   - If interrupted mid-transaction: RF output corrupted
   - Causes: frequency glitches, CW keying artifacts, audio clicks

4. I2C BIT-BANGING IS NOT ATOMIC
   - Each byte requires 8 bit operations
   - Each bit operation involves GPIO read/write sequences
   - If another thread enters between bit operations: bus corrupted
   - Slave device (Si5351) sees nonsense, returns NACK

================================================================================
DEVICES ON I2C BUS
================================================================================

Si5351 (0x60)      RX/TX Local Oscillator Frequency Control    [TIMING-CRITICAL]
Si570 (0x55)       Alternative frequency source               [HIGH PRIORITY]
DS3231 (0x68)      Real-Time Clock                            [NON-CRITICAL]
INA260 (0x40)      Power monitoring (voltage/current)         [NON-CRITICAL]
ZBitx (0x0A)       Remote display interface                   [NON-CRITICAL]

The Si5351 is the culprit - it's accessed during frequency changes which
happen frequently from multiple threads.

================================================================================
IMPACT ASSESSMENT
================================================================================

When "double!" warning appears:
  1. At least 2 threads have entered i2c_write_byte() simultaneously
  2. Both are trying to write to GPIO pins
  3. Bus state is undefined
  4. Si5351 receives partial/corrupted frequency value
  5. RF output frequency is wrong
  6. Audio quality degraded (clicks, pops, distortion)
  7. CW keying becomes unreliable

Frequency glitches during:
  - Rapid tuning while RTC is being read
  - Network command while UI tuning
  - Calibration thread running while user operates

================================================================================
THE FIX
================================================================================

REQUIRED: Add pthread_mutex protection to ALL I2C entry points

1. Add to i2cbb.c:
   #include <pthread.h>
   static pthread_mutex_t i2c_bus_mutex = PTHREAD_MUTEX_INITIALIZER;

2. Wrap ALL I2C transactions:
   pthread_mutex_lock(&i2c_bus_mutex);
   [I2C operation]
   pthread_mutex_unlock(&i2c_bus_mutex);

3. Functions to fix:
   - i2cbb_write_byte_data()
   - i2cbb_read_byte_data()
   - i2cbb_write_i2c_block_data()
   - i2cbb_read_i2c_block_data()
   - i2cbb_read_rll()

4. Remove the fake static int mutex (lines 196-199, 211)
5. Replace spin-wait i2c_busy with proper mutex
